M-16-EMeasurementPaneContainer

PaneContainer 측정 하네스 구현 보고서

이번 작업은 PaneContainerControl 구조를 바로 뒤엎지 않고, 현재 구조가 실제로 비용을 만드는지 자동으로 확인할 수 있는 측정 경로를 추가한다. 2026-05-11 추가 검증에서는 일반창에서 더 잘 보이던 active terminal border 잘림까지 실제 화면 캡처 기반으로 잡고 수정했다.

핵심 결론

방향

측정 우선. 현재 수치만으로는 PaneContainer visual tree 재작성을 정당화할 근거가 약하다.

추가된 검증

pane-split-churn, workspace-switch-churn measurement scenario와 focus-only fast path 단위 테스트를 추가했다.

산출물

기존 render-perf.csv, cpu.csv에 더해 split/workspace action timing, pane geometry, 화면 캡처 PNG를 sidecar로 남긴다.

중요 수정

측정 실행 중 child shell stdout이 measurement log로 새어 terminal 화면이 비는 launch 버그를 발견했고 수정했다.

시각 게이트

visual-window.png를 실제 창에서 캡처하고 각 pane crop에서 텍스트 픽셀과 active border 4변을 판정한다.

보더 수정

WPF frame은 layout 공간만 예약하고, 실제 active border는 DX surface 내부에서 그리도록 변경했다.

현재 구조

TerminalPaneLayoutViewModel
  -> TerminalPaneLayoutSnapshot
  -> PaneContainerControl.Layout
     -> shape key 비교
        -> 같음: UpdateFocusVisuals()
        -> 다름: BuildGrid() / BuildElement()
             -> TerminalHostControl reuse/create
             -> child HWND / RenderSurface

중요한 점은 focus 상태가 shape key에 들어가지 않는다는 것이다. 따라서 focus만 바뀌는 layout update는 Content를 교체하지 않고 기존 visual tree와 host를 유지해야 한다.

일반창 active border 잘림

사용자가 제공한 일반창/전체화면 비교에서 일반창은 active terminal의 오른쪽/아래 border가 더 확실히 잘려 보였다. 실제 검증에서도 WPF Border 두께를 0.5에서 1 DIP로 바꾸는 것만으로는 문제가 끝나지 않았다. TerminalHostControl은 HwndHost라서 child HWND가 별도 Win32 airspace를 갖고, DPI 150% 같은 환경에서 물리 픽셀 반올림이 일어나면 WPF sibling stroke가 오른쪽/아래에서 가려질 수 있다.

최종 수정은 기존 설계를 유지하는 방식으로 했다. PaneContainerControl은 여전히 layout/focus/workspace 경계만 담당하고, WPF frame은 1 DIP 공간을 안정적으로 예약한다. 화면에 보이는 active border는 focused_surface_id를 가진 DX surface 내부에 2px overlay quad 4개로 그린다. 이렇게 하면 child HWND 바깥의 WPF 선을 믿지 않고, 터미널 내용과 같은 native render pass 안에서 보더가 같이 그려진다.

추가로 workspace 전환 후 cached host가 다시 붙는 경우 active surface가 흐려질 수 있어, PaneContainerControl.ApplyLayout이 layout 적용 뒤 SurfaceCoordinator.FocusPane을 재호출하도록 했다. PaneLayoutService.SetFocused도 같은 pane 재선택을 조기 반환하지 않고 native SurfaceFocus와 active session을 다시 확정한다.

측정 실행 환경 버그

사용자가 “오래 켜져도 터미널 내부 내용이 렌더링되지 않는다”고 관찰한 뒤 재측정했다. 원인은 native DLL 누락이 아니라, measurement script가 GhostWin.App을 UseShellExecute=false로 실행하면서 redirected stdout/stderr handle을 앱에 상속시킨 것이다.

이 상태에서는 child pwsh 출력이 ConPTY/GhostWin surface가 아니라 measurement stdout으로 새어 화면에는 배경과 커서만 보였다. Start-GhostWinApp를 Start-Process 기반으로 바꾸고 환경 변수만 일시 설정하도록 수정한 뒤, 같은 20초 측정에서 stdout 누수가 사라지고 4-pane 모두 텍스트가 보였다.

실행 중 발견한 shutdown race

첫 Release 측정에서는 summary와 artifact 생성 후 앱 종료 직후 gw_session_get_scrollback_info 호출 중 native access violation이 발생했다. 원인은 숨긴 창이 곧바로 unload되지 않아 PaneContainerControl의 100ms scrollbar poll timer가 엔진 destroy와 겹친 것이다.

수정은 종료 경로에서 PaneContainer.StopScrollPolling()을 먼저 호출하는 방식이다. 재실행 결과 같은 scenario가 종료 crash 없이 통과했다.

요약 한 줄

M-16-E는 “PaneContainer를 바로 고치는 작업”이 아니라 “분할/워크스페이스 전환에서 고쳐야 할 만큼 문제가 있는지 자동으로 증명하는 작업”으로 정리했다. 이번 재측정에서는 visual tree 재작성보다 측정 launch 계약, DPI-aware visual proof, 그리고 HwndHost 경계 밖이 아니라 DX surface 내부에서 active border를 그리는 방식이 실제 해결책이었다.
