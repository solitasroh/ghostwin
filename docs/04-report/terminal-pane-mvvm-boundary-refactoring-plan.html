Terminal Pane MVVM Boundary Refactoring Plan

GhostWin.App의 pane/grid/splitter 생성 구조를 재검토한 결과, 문제는 code-behind에서 Grid를 만드는 행위 자체가 아니라 View가 상태, 명령, 서비스 조정, native lifecycle까지 함께 들고 있는 경계 붕괴다. 이 문서는 그 경계를 단계적으로 복구하는 계획이다.

작성일2026-05-09
대상GhostWin.App / PaneContainerControl / TerminalHostControl
권장 방향pane마다 host 유지, View는 renderer로 축소
비권장 방향단일 TerminalHostControl 전환은 native compositor 재설계 없이는 보류

1. 결론

Grid와 GridSplitter를 code-behind에서 구성하는 것은 현재 구조에서 허용 가능한 선택이다. pane tree가 런타임에 재귀적으로 바뀌고, 각 leaf에 HwndHost와 DX11 child HWND를 붙여야 하기 때문이다.

하지만 현재 PaneContainerControl은 단순 renderer가 아니다. workspace/pane state, host cache, scroll state, settings, engine 호출, context menu command, zoom까지 직접 처리한다. 이 부분이 MVVM 기반 구조를 깨는 실제 원인이다.
질문 판단 이유
Grid/GridSplitter를 code-behind로 만드는 것이 틀렸나? 아님 동적 pane tree + HwndHost attach/detach는 XAML 바인딩만으로 다루기 어렵다.
PaneContainerControl이 지금처럼 모든 책임을 들고 있어도 되나? 아님 View가 controller/service coordinator 역할까지 겸한다.
TerminalHostControl을 앱 전체 하나로 줄여야 하나? 보류 현재 native 계약은 HWND 1개와 swapchain 1개가 RenderSurface 1개에 묶이는 구조다.
이번 리팩터링의 1차 목표는? 경계 복구 View는 visual tree renderer, host는 native adapter, 상태/명령/정책은 VM/service로 이동한다.

2. 코드 근거

근거 파일 판단
PaneContainerControl이 host cache, scroll bar, engine, settings를 직접 소유 src/GhostWin.App/Controls/PaneContainerControl.cs lines 21, 32, 88-90 View 책임 초과. host cache 일부는 필요하지만 engine/settings 직접 참조는 분리 대상.
BuildElement()가 leaf마다 host 생성/재사용, border, scrollbar, context menu를 함께 조립 PaneContainerControl.cs lines 252, 295, 324, 507, 605 visual tree 조립은 유지 가능. command/policy/state는 분리해야 한다.
TerminalHostControl이 child HWND를 만들고 WndProc를 직접 받음 TerminalHostControl.cs lines 20, 88, 115 native boundary. MVVM으로 없애기보다 얇은 adapter로 정리해야 한다.
Ctrl+Wheel이 host 내부에서 settings 저장과 message 발행까지 수행 TerminalHostControl.cs line 278 명령/설정 정책이 View에 들어간 설계 부채.

native RenderSurface가 HWND, session id, swapchain, RTV를 보유 src/engine-api/surface_manager.h line 30 pane별 host/surface 구조를 유지해야 하는 강한 근거.
DXGI swapchain은 CreateSwapChainForHwnd로 특정 HWND에 붙음 src/engine-api/surface_manager.cpp line 27 단일 host 전환은 native compositor 설계 없이는 리스크가 크다.

3. 목표 아키텍처

핵심은 code-behind를 제거하는 것이 아니라, code-behind가 맡을 수밖에 없는 일을 명확히 줄이는 것이다. 아래처럼 boundary를 나누면 Grid/GridSplitter 조립은 View에 남겨도 MVVM 흐름은 회복할 수 있다.

PaneLayoutViewModelRoot pane tree, focused pane, split ratio, pane commands
→
PaneContainerControlVM tree를 Grid/GridSplitter/Host visual tree로 변환
→
TerminalHostControlHwndHost 생성, raw native event forwarding
TerminalSurfaceCoordinatorHostReady, Resize, Focus를 SurfaceCreate/Resize/Focus로 연결
↔
TerminalInputRouterKey/mouse/context/wheel을 command와 engine call로 라우팅
↔
IEngineServicenative engine boundary
컴포넌트 남길 책임 빼낼 책임
PaneContainerControl VM tree를 WPF visual tree로 렌더링, host attach/detach, GridSplitter 생성 messenger 구독, settings 조회, engine 호출, scrollback policy, pane command 실행
TerminalHostControl BuildWindowCore, DestroyWindowCore, WndProc, Win32 cursor/set size settings 저장, clipboard policy, external launcher, context menu command 구현
PaneLayoutViewModel pane tree projection, focus/selection metadata, split/close/zoom command surface native HWND 생성, DX11 호출 직접 수행
TerminalSurfaceCoordinator host lifecycle event를 surface lifecycle로 변환, failure/retry policy 관리 WPF visual tree 생성
TerminalInputRouter WPF/HWND input event를 app command 또는 engine write로 분류 ViewModel property 변경 직접 수행

4. 이번 리팩터링에서 하지 않을 것

단일 TerminalHostControl 전환 보류

현재 renderer는 pane별 HWND/swapchain/surface 계약 위에 있다. 단일 host는 native compositor, hit-test, clipping, accessibility를 새로 설계해야 한다.

ItemsControl 기반 완전 XAML화 보류

live HwndHost와 swapchain은 WPF virtualized item처럼 안전하게 recycle하기 어렵다. VM tree는 가능하지만 host 자체의 완전 가상화는 별도 과제다.

뒤엎는 결정을 내릴 수 있는 조건

  • pane별 child HWND airspace 때문에 해결 불가능한 overlay/UI 요구가 반복 발생한다.
  • 8-pane 제한 안에서도 swapchain/HWND 수가 측정상 명확한 병목으로 확인된다.
  • focus/resize/surface lifecycle 버그가 host별 구조 자체에서 반복되고, coordinator 분리로도 줄지 않는다.
  • native compositor를 도입해도 IME, selection, context menu, accessibility를 회귀 없이 재구성할 테스트 기반이 준비된다.

5. 단계별 리팩터링 계획

Phase 0 — Characterization Baseline

목표: 구조를 만지기 전에 현재 동작을 고정한다. 이 단계는 기능 추가가 아니라 회귀 방지망이다.

  • split vertical/horizontal 후 pane count와 focused pane이 유지되는 테스트를 확인한다.
  • workspace switch 후 host 재사용과 surface 중복 생성 여부를 로그로 확인한다.
  • Ctrl+Wheel, Shift+Wheel, right click, selection, IME preview의 현재 동작을 smoke 체크리스트로 고정한다.
  • SurfaceCreate 실패 시 blank pane이 되는 현재 동작을 기록하고, 이후 coordinator에서 개선 대상으로 둔다.

수정 후보: tests/GhostWin.App.Tests, tests/GhostWin.Automation.*, RenderDiag log 기준 smoke script

Phase 1 — Pane ViewModel Projection 도입

목표: IReadOnlyPaneNode를 View가 직접 읽지 않고, UI에 필요한 shape로 projection한다.

  • TerminalPaneNodeViewModel을 추가한다. leaf는 PaneId, SessionId, IsFocused, Scrollbar, Commands를 가진다.
  • split node는 SplitDirection, Ratio, Left, Right를 가진다.
  • PaneLayoutViewModel이 active workspace의 pane tree를 구독하고 Root VM을 갱신한다.
  • 초기에는 기존 IPaneLayoutService.Root를 그대로 projection해 behavior 변경을 최소화한다.

수정 후보: src/GhostWin.App/ViewModels/PaneLayoutViewModel.cs, TerminalPaneNodeViewModel.cs, MainWindowViewModel.cs

Phase 2 — PaneContainerControl을 Renderer로 축소

목표: PaneContainerControl이 service locator와 messenger에서 벗어나 Root VM을 받는 custom renderer가 된다.

  • Root dependency property 또는 명시적 SetRoot(TerminalPaneNodeViewModel?)를 추가한다.
  • BuildElement() 입력을 IReadOnlyPaneNode에서 TerminalPaneNodeViewModel로 바꾼다.
  • host cache는 renderer 내부에 남기되, active workspace/pane state는 VM에서 전달받는다.
  • Ioc.Default.GetService, direct messenger registration, settings read를 제거한다.

수정 후보: src/GhostWin.App/Controls/PaneContainerControl.cs, MainWindow.xaml

Phase 3 — TerminalSurfaceCoordinator 분리

목표: HostReady/Resize/Focus event를 surface lifecycle로 변환하는 책임을 View에서 분리한다.

  • ITerminalSurfaceCoordinator를 추가한다.
  • OnHostReady(paneId, sessionId, hwnd, width, height)가 SurfaceCreate를 호출하고 pane state에 surface id를 반영한다.
  • OnHostResized, OnPaneFocused, OnHostDisposed를 coordinator로 옮긴다.
  • 현재 PaneLayoutService.OnHostReady()의 silent return/failure logging은 coordinator로 옮기고 retry/error UI 정책을 넣을 여지를 만든다.

수정 후보: src/GhostWin.Core/Interfaces/ITerminalSurfaceCoordinator.cs, src/GhostWin.Services/TerminalSurfaceCoordinator.cs, PaneLayoutService.cs

Phase 4 — TerminalInputRouter 분리

목표: TerminalHostControl은 raw event를 내보내고, command/engine write/settings 변경은 router가 결정한다.

  • WndProc에서 mouse event를 구조화된 event로 변환한다.
  • selection, wheel, context menu request, paste/copy/open external command를 router 또는 command service로 이동한다.
  • Ctrl+Wheel font size 변경은 SettingsPageViewModel이나 settings command service와 같은 정책 계층으로 옮긴다.
  • MainWindow의 terminal key handling과 VM command 중복을 줄이고, HwndHost가 삼키는 입력만 router fallback으로 둔다.

수정 후보: src/GhostWin.App/Input/TerminalInputRouter.cs, TerminalHostControl.cs, MainWindow.xaml.cs

Phase 5 — ScrollBar와 ContextMenu를 VM Command 기반으로 이동

목표: visual 생성은 View가 하되, 표시 여부와 command는 VM이 결정한다.

  • TerminalPaneScrollbarViewModel 또는 leaf VM 속성으로 Maximum, Value, ViewportSize, Visibility를 제공한다.
  • polling은 임시로 coordinator/service에 남기고, View는 바인딩된 상태만 표시한다.
  • pane context menu item은 VM command에 바인딩한다.
  • zoom state는 PaneLayoutViewModel 또는 별도 PanePresentationState로 이동한다.

수정 후보: PaneContainerControl.cs, PaneLayoutViewModel.cs, terminal pane command classes

Phase 6 — Cleanup and Documentation

목표: 새 boundary를 문서화하고 남은 View/ViewModel 누수를 후속 backlog로 정리한다.

  • Obsidian Architecture/wpf-shell에 새 boundary를 반영한다.
  • Tech Debt에서 이번 항목을 completed 또는 remaining mini로 갱신한다.
  • MainWindowViewModel의 WPF ResourceDictionary/theme 접근, WorkspaceItemViewModel의 service locator는 별도 mini로 분리할지 결정한다.
  • 이 계획에서 제외한 단일 native compositor는 별도 ADR 후보로 남긴다.

7. 주요 위험과 완화

위험 영향 완화책
HostReady ordering 회귀 초기 pane blank, surface create 누락 MainWindow.InitializeRenderer의 no-yield 계약을 유지하고, coordinator도 동기 등록 후 workspace 생성 순서를 지킨다.
host 재사용 실패 split/close 때 HWND/swapchain 재생성 증가, flicker, surface leak pane id 우선, session id fallback 재사용 규칙을 그대로 보존한다.
VM tree 갱신이 visual tree 전체 rebuild를 과도하게 유발 resize/focus 성능 저하 초기에는 현재 BuildGrid 수준으로 제한하고, 이후 diff update는 별도 M-16-E 성격의 측정 후 결정한다.
input router 분리 중 shortcuts 회귀 터미널 사용성 직접 저하 기존 key handling을 한 번에 제거하지 않고, router가 동일 branch를 통과하게 만든 뒤 중복 제거한다.
scope creep native compositor 또는 Core 모델 정화까지 번짐 이번 cycle은 terminal pane boundary에 한정한다. Core model purity와 single compositor는 별도 ADR/backlog로 분리한다.

8. 실행 단위 제안

한 번에 다 바꾸면 HostReady, WndProc, surface lifecycle, input shortcut이 동시에 흔들린다. 작업은 아래 4개 PR 또는 PDCA batch로 자르는 것이 안전하다.

  1. Batch A: VM projection만 추가하고 기존 renderer는 그대로 사용한다. behavior 변경 0을 목표로 한다.
  2. Batch B: PaneContainerControl 입력을 Root VM으로 바꾸고 service locator/messenger를 제거한다.
  3. Batch C: surface coordinator를 도입해 HostReady/Resize/Focus 경계를 분리한다.
  4. Batch D: input router, scrollbar VM, context menu command를 분리한다.
권장 선행 마일스톤 이름: Terminal Pane MVVM Boundary. 성공 기준은 “code-behind 0”이 아니라 “View가 visual/native adapter 책임만 들고, 상태와 명령은 VM/service에서 추적 가능”이다.

9. 2026-05-09 실행 결과

마라톤 구현으로 Batch A-D를 모두 반영했다. PaneContainerControl은 bound layout snapshot을 받아 WPF visual tree와 HwndHost cache를 구성하는 renderer로 축소됐고, surface lifecycle, scrollbar state, pane command/zoom, terminal input/settings/context command는 coordinator/service 경계로 이동했다.

범위 상태 결과
Batch A — VM projection 완료 TerminalPaneNodeViewModel, TerminalPaneLayoutViewModel, TerminalPaneLayoutSnapshot 추가
Batch B — PaneContainer 입력 경계 완료 PaneContainerControl.Layout 바인딩으로 전환하고, layout/focus/workspace messenger 직접 수신 제거
Batch C — lifecycle coordinator 완료 ITerminalSurfaceCoordinator, ITerminalSurfaceLayout 추가. HostReady/Resize/Click은 host workspace id 기준으로 coordinator가 라우팅
Batch D — command/input/scroll 분리 완료 TerminalInputRouter, TerminalPaneScrollService, TerminalPaneCommandService로 wheel/settings, paste/write, terminal context command, scrollbar projection, split/close/zoom 정책 이동
검증: GhostWin.App.Tests 94/94 PASS, GhostWin.Core.Tests 40/40 PASS, git diff --check 오류 0. 신규 테스트는 VM projection/snapshot, stale focus 방어, idempotent registration, Initialize 전 Layout defer, workspace별 HostReady/Resize 라우팅, inactive click 무시, closed workspace cache 제거, surface coordinator, input router, scrollbar state projection, pane command/zoom service를 포함한다.
