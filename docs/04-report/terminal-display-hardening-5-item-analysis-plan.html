GhostWin Terminal Display Hardening

기존 터미널 UI 표시 구조 분석에서 도출된 문제를 5개 항목으로 재분해하고, 코드 근거, 사용자 체감 실패, 구현 순서, 검증 방법을 다시 정리한 실행 계획서.

작성일: 2026-05-10 범위: GhostWin.App / GhostWin.Services / engine-api / renderer / session 기준 브랜치: feature/wpf-migration 이전 완료: terminal-pane-mvvm-boundary

요약

Grid와 GridSplitter를 code-behind에서 조립하는 것 자체가 이번 결함의 원인은 아니다. 현재 남은 위험은 View/ViewModel 경계 밖의 native surface 표시 계약에 있다. 즉, pane tree를 VM snapshot으로 밀어낸 뒤에도 RenderSurface, DXGI swapchain, render thread, native session registry, child HWND 실패 UX가 따로 닫혀야 한다.

5개 항목은 한 사이클로 묶되, 구현은 표시 invalidation, resize 동시성, DXGI 실패 처리, session registry 잠금, SurfaceCreate 실패 UX 순으로 진행하는 것이 안전하다.

결론

P1로 잡아야 할 항목은 4개다. focus dim invalidation, resize payload race, ResizeBuffers hardening, session lookup race는 표시 오류나 crash로 이어질 수 있다.

SurfaceCreate failure UX는 crash 가능성은 낮지만, 한 번 실패한 pane이 영구 blank 상태로 남아 사용자 체감 영향이 크다.

구현 결과 - 2026-05-10

계획한 5개 항목을 한 사이클로 구현했다. surface-local dirty epoch, resize request 소비 계약, per-surface ResizeBuffers HRESULT 처리, SessionManager registry lock, SurfaceCreate 실패 placeholder/retry를 추가했다.

4. 항목 1 - focus dim invalidation

핵심 문제: gw_surface_focus()가 각 surface의 dim_factor를 바꾸지만, render loop의 skip 조건은 vt_dirty, visual_dirty, resize_applied만 본다. 따라서 focus만 바뀌고 터미널 출력이나 selection/IME/resize가 없으면 dim overlay가 다시 그려지지 않을 수 있다.

코드 근거

파일근거의미
ghostwin_engine.cpp render_surface()가 visual_dirty = last_visual_epoch != visual.epoch 계산 후 skip session visual epoch만 보고 surface-local dim 변경은 보지 않음
ghostwin_engine.cpp dim overlay quad append는 skip 이후에만 실행 skip되면 변경된 dim 값을 읽을 기회가 없음
surface_manager.h RenderSurface.dim_factor는 atomic float이고 dirty epoch와 연결되지 않음 값 변경 자체가 repaint 이유가 되지 않음
session_manager.cpp activate()는 새 active session의 visual_state.bump_epoch()만 호출 이전 pane이 어두워져야 하는 경우에는 epoch가 오르지 않을 수 있음
PaneLayoutService.cs SplitFocused()는 새 pane을 focused로 바꾸지만 새 surface 생성 전이라 SurfaceFocus를 못 부름 split 직후 dim 초기화가 늦거나 누락될 수 있음

실패 시나리오

1. 두 개 pane이 idle 상태다. VT 출력도 없고 IME/selection 변경도 없다.
2. 사용자가 다른 pane을 클릭한다.
3. gw_surface_focus()는 이전 pane의 dim_factor를 0.4로 바꾼다.
4. 다음 render frame에서 vt_dirty=false, visual_dirty=false, resize_applied=false라면 바로 return한다.
5. 실제 focus는 바뀌었는데 이전 pane이 밝은 상태로 남는다. 다음 출력이나 resize가 있어야 뒤늦게 반영된다.

선택할 해결안

surface-local visual epoch를 추가한다. dim은 session 상태가 아니라 surface 표시 상태이므로 SessionVisualState에 얹지 않는다. 

struct RenderSurface {
    std::atomic<uint64_t> visual_epoch{1};
    uint64_t last_surface_visual_epoch = 0; // render thread only
    std::atomic<float> dim_factor{0.0f};
};

void set_surface_dim(RenderSurface& s, float value) {
    float old = s.dim_factor.exchange(value, std::memory_order_acq_rel);
    if (old != value) {
        s.visual_epoch.fetch_add(1, std::memory_order_release);
    }
}

render loop는 기존 visual_dirty와 별도로 surface_visual_dirty = surf->last_surface_visual_epoch != surf->visual_epoch.load(...)를 계산하고, skip 조건에 포함한다. Present가 성공했을 때만 last_surface_visual_epoch를 갱신한다.

부가 수정

  • gw_surface_focus()에서 모든 surface에 대해 dim target을 계산하되, 값이 실제로 바뀐 surface만 epoch를 올린다.
  • AttachHostSurface()에서 새 surface를 만든 pane이 현재 focused pane이면 즉시 SurfaceFocus(surfaceId)를 호출한다. split 직후 dim 초기화 누락을 같이 닫는다.
  • render perf log에 skip하지 않은 이유를 선택적으로 남긴다: vt, session_visual, surface_visual, resize.

레벨검증합격 기준
Native unit dim factor 변경 시 epoch 증가, 같은 값 재설정 시 증가 없음 surface-local dirty reason이 정확히 발생
Render gate VT dirty 없음, session visual 변경 없음, resize 없음, surface visual만 변경 render가 skip하지 않음

5. 항목 2 - surface resize payload race

핵심 문제: SurfaceManager::resize()는 mutex 아래에서 plain pending_w/h를 쓰지만, render thread는 mutex 없이 needs_resize atomic flag만 보고 plain field를 읽는다. 이는 C++ 기준 data race이며, 더 늦게 들어온 resize 요청을 render thread가 false 저장으로 지울 수도 있다.

현재 흐름

WPF size changedTerminalHostControl.OnRenderSizeChanged
CoordinatorOnHostResized(workspace,pane,w,h)
PaneLayoutServiceSurfaceResize(surfaceId,w,h)
SurfaceManagerpending_w/h 쓰고 needs_resize=true
Render threadflag 보고 payload 읽은 뒤 ResizeBuffers

문제의 정확한 형태

문제현재 코드 모양사용자 체감
payload data race pending_w/h는 plain field, writer와 reader가 같은 lock을 쓰지 않음 드문 crash, 잘못된 크기, black pane
width/height pair 불일치 render가 width는 이전 요청, height는 다음 요청에서 읽을 수 있음 한 프레임 이상 비정상 aspect, mouse hit-test 어긋남
latest resize 유실 render가 요청 A 처리 중 요청 B가 들어온 뒤 마지막에 needs_resize=false 저장 최종 창 크기와 swapchain 크기가 다를 수 있음
applied size 경쟁 width_px/height_px도 render thread write, 다른 경로 read mouse encoding, padding 계산, overlay size가 흔들릴 수 있음

선택할 해결안

per-surface resize request lock + atomic applied size를 선택한다. 지금 구조에 가장 적게 침투하면서 payload 일관성과 최신 요청 유실을 같이 막을 수 있다. 

struct SurfaceResizeRequest {
    uint32_t width_px = 0;
    uint32_t height_px = 0;
    uint64_t sequence = 0;
};

struct RenderSurface {
    mutable std::mutex resize_mutex;
    SurfaceResizeRequest pending_resize;
    uint64_t resize_sequence = 0;
    bool resize_pending = false;
    std::atomic<uint64_t> applied_size_packed{0};
};

bool consume_resize(RenderSurface& s, SurfaceResizeRequest& out) {
    std::lock_guard lock(s.resize_mutex);
    if (!s.resize_pending) return false;
    out = s.pending_resize;
    s.resize_pending = false;
    return true;
}

SurfaceManager::resize()는 surface map lock으로 대상 surface를 찾은 뒤, surface의 resize_mutex 아래에서 pending request를 갱신한다. render thread는 consume_resize()로 한 번에 request를 가져오고 lock을 풀고 나서 ResizeBuffers를 수행한다.

중요한 정책

  • ResizeBuffers가 성공했을 때만 applied size를 갱신한다.
  • 실패하면 방금 소비한 request를 retry 대상으로 다시 넣거나 surface failure state로 전환한다. 실패한 크기를 성공한 것처럼 기록하지 않는다.
  • mouse/padding 등 다른 reader는 applied_size_packed에서 일관된 width/height pair를 읽는다.
  • 0 크기는 WPF 쪽과 native 쪽에서 모두 1 이상으로 clamp한다.

6. 항목 3 - ResizeBuffers hardening / device-lost fallback

핵심 문제: per-surface resize path는 ResizeBuffers, GetBuffer, CreateRenderTargetView 결과를 확인하지 않고, 실패해도 surface size를 갱신하고 flag를 내릴 수 있다. 또한 context가 이전 RTV를 잡고 있는 상태에서 resize할 수 있고, device-lost는 Present 로그만 남긴다.

현재와 legacy 경로 비교

항목legacy renderer resizeper-surface resize판단
context 정리 ClearState() 호출 renderer->unbind_surface()는 draw 후 ComPtr reset만 수행 per-surface가 약함
ResizeBuffers 확인 HRESULT 실패 로그 후 return HRESULT 미확인 per-surface가 실패를 성공처럼 볼 수 있음
RTV 재생성 create_rtv() 호출 GetBuffer, CreateRTV 결과 미확인 black pane 원인 추적이 어려움
device-lost 초기 device 생성은 HW 실패 시 WARP fallback runtime device-lost 복구 없음 GPU reset 후 회복 불가

선택할 해결안

render loop 안에 흩어진 resize 코드를 빼서 surface resize helper로 격리한다. helper는 DXGI 호출 결과를 구조화해서 반환하고, render loop는 성공/실패에 따라 surface 상태만 갱신한다. 

enum class SurfaceResizeStage {
    None,
    UnbindContext,
    ResizeBuffers,
    GetBackBuffer,
    CreateRenderTargetView,
    DeviceLost
};

struct SurfaceResizeResult {
    bool ok = false;
    SurfaceResizeStage stage = SurfaceResizeStage::None;
    HRESULT hr = S_OK;
    bool device_lost = false;
};

SurfaceResizeResult apply_surface_resize(RenderSurface& s,
                                         const SurfaceResizeRequest& req);

DX11 처리 정책

  • ResizeBuffers 전 OMSetRenderTargets(0, nullptr, nullptr) 또는 전용 release_surface_bindings()로 context가 잡은 RTV reference를 끊는다.
  • 필요 시 Flush()를 호출해 resize 직전 reference release를 명확히 한다. 단, 매 frame 비용이 되지 않도록 resize 때만 수행한다.
  • ResizeBuffers, GetBuffer, CreateRenderTargetView의 HRESULT를 모두 확인한다.
  • 성공한 경우에만 rtv, applied size, resize epoch를 갱신한다.
  • 실패하면 surface id, session id, old size, requested size, stage, hr를 로그에 남기고 retry 또는 failed state로 보낸다.

device-lost 단계화

단계내용이번 사이클 포함 여부
1. 감지 Present, ResizeBuffers, Map, CreateBuffer 실패에서 DXGI_ERROR_DEVICE_REMOVED/RESET/HUNG 분류 포함
2. 상세 로그 GetDeviceRemovedReason()를 남기고 engine-level device state를 Lost로 전환 포함
3. graceful degrade render thread가 무한 실패하지 않고 pane surface status를 failed로 올림 포함
4. full rebuild renderer, atlas, SurfaceManager를 재생성하고 HWND/session/size metadata로 surface 재생성 후속 또는 이번 사이클 후반. 위험하면 별도 작업으로 분리

검증 계획

  • test hook으로 ResizeBuffers, GetBuffer, CreateRTV, Present 실패를 주입한다.
  • per-surface resize smoke test를 추가한다. 기존 dx11_render_test는 legacy resize만 타므로 충분하지 않다.
  • GHOSTWIN_LOG_FILE에 stage, surface id, session id, hr가 남는지 검증한다.
  • device-lost injection 후 render thread가 바쁘게 실패를 반복하지 않고 명시 상태로 멈추거나 복구 루틴을 탄다.

7. 항목 4 - render thread session lookup / lifetime race

핵심 문제: SessionManager::get()은 any thread API이고 shared_ptr<Session>를 반환한다. 이 반환값은 찾은 뒤의 객체 수명은 보호하지만, sessions_ vector를 찾는 과정 자체는 보호하지 않는다. render thread가 순회하는 동안 UI/main thread가 split/close/create로 vector를 push/erase하면 data race와 iterator invalidation이 생긴다.

현재 수명 보호의 한계

대상현재 보호남은 구멍
RenderSurface SurfaceManager::active_surfaces()가 shared_ptr snapshot 반환 surface 객체 수명은 비교적 안전함
Session 객체 get() 성공 후 shared_ptr가 객체 생존을 연장 lookup 성공 이후만 안전함
sessions_ vector 주석상 writer는 main thread only, reader는 any thread reader/writer가 같은 lock을 쓰지 않음

실패 시나리오

1. render thread가 render_surface()에서 session_mgr->get(surf->session_id)를 호출한다.
2. get()은 lock 없이 sessions_ vector를 순회한다.
3. 동시에 UI/main thread가 pane split로 session을 create하거나 close로 erase한다.
4. vector reallocation 또는 erase로 iterator가 무효화될 수 있다.
5. 결과는 드문 access violation, 잘못된 session 렌더링, shutdown 근처 crash로 나타날 수 있다.

선택할 해결안

SessionManager에 std::shared_mutex를 추가한다. 읽기 API는 shared lock, vector를 바꾸는 API는 unique lock을 쓴다. 단, TSF 호출과 managed callback은 lock 밖에서 실행해야 한다. 

class SessionManager {
    mutable std::shared_mutex sessions_mutex_;
    std::vector<std::shared_ptr<Session>> sessions_;
};

std::shared_ptr<Session> SessionManager::get(SessionId id) {
    std::shared_lock lock(sessions_mutex_);
    auto it = find_by_id_locked(id);
    return it != sessions_.end() ? *it : nullptr;
}

lock 설계 원칙

원칙이유적용 위치
callbacks outside lock 콜백이 다시 engine/session API를 부르면 교착 상태가 될 수 있음 fire_event, child exit, title/cwd callbacks
TSF outside lock COM/TSF 호출은 재진입 가능성이 있고 UI thread affinity가 있음 switch_tsf_focus, focus/unfocus
private locked helpers activate(), close_session()이 서로 호출하면 lock 재진입 위험이 있음 find_by_id_locked, activate_locked_no_events
shared_ptr copy under lock vector 조회 중 안전하게 strong reference를 확보해야 함 get, active_session, ids

구현 형태

  1. sessions_mutex_와 locked helper를 추가한다.
  2. get, active_session, count, ids, id_at, index_of에 shared lock을 적용한다.
  3. create_session, close_session, move_session, destructor cleanup 준비 구간에 unique lock을 적용한다.
  4. close_session은 lock 안에서 상태 변경과 vector erase만 수행하고, TSF focus 전환과 event fire는 lock 밖으로 분리한다.
  5. render loop의 get() 호출은 그대로 두되, lookup 자체가 안전해졌음을 native stress로 확인한다.

검증 계획

  • native stress: 한 thread는 get(), active_session(), ids() 반복. 다른 thread는 create/close 반복.
  • render-integrated stress: render thread가 surface를 순회하는 동안 split/close/create를 빠르게 반복.
  • App automation: test control로 split vertical/horizontal/close를 1,000회 이상 반복하고 crash와 blank pane을 확인.
  • 가능하면 별도 clang-cl/LLVM 빌드에서 ThreadSanitizer 후보를 검토한다. VS 중심이면 deterministic stress를 우선 둔다.

8. 항목 5 - SurfaceCreate failure UX / retry

핵심 문제: SurfaceCreate가 실패하면 native는 0을 반환하고, PaneLayoutService는 로그만 남긴 뒤 SurfaceId=0 상태로 둔다. 이후 resize는 바로 return하므로 pane은 영구 blank가 될 수 있고, 사용자는 retry할 방법이 없다.

현재 실패 흐름

CreateWindowExchild HWND 생성 실패 가능. 현재 last error 수집 부족
HostReadyhwnd=0도 전달될 수 있음
SurfaceCreatenative 실패 시 0 반환
PaneLayoutServiceTrace error 후 return
Blank panesurface 없음, retry 없음, visible error 없음

선택할 해결안

surface 상태를 ViewModel snapshot까지 올리고, 실패 시 host 대신 placeholder를 렌더링한다. HwndHost airspace 문제 때문에 WPF overlay를 native child HWND 위에 얹기보다, failed 상태에서는 host를 숨기거나 대체 content를 보여주는 방식이 안전하다.

데이터 모델

Native result 구조화

현재개선이유
uint SurfaceCreate(...), 실패는 0 SurfaceCreateResult 추가, 기존 API는 shim으로 유지 stage/hr가 없으면 UX와 자동 retry 판단을 할 수 없음
native 로그와 C# Trace가 분리됨 workspace/pane/session/attempt correlation field를 공통으로 남김 blank pane 원인을 한 로그 흐름으로 추적
RTV create 실패 로그 부족 GetBuffer, CreateRTV stage별 HRESULT 기록 DXGI failure와 UX failure를 연결

Retry 정책

  • 자동 retry는 1-2회만 허용한다. 초기 timing/driver transient에는 도움이 되지만 무한 반복은 피한다.
  • hwnd != 0이고 host가 살아 있으면 기존 HWND로 native bind를 재시도한다.
  • hwnd == 0이거나 stale host라면 host recreate가 필요하므로 VM snapshot에 NeedsHostRecreate 성격의 상태를 올린다.
  • retry 성공 시 Ready로 전환하고, focused pane이면 SurfaceFocus를 다시 호출한다.
  • retry 실패 시 attempt와 stage를 갱신하고 placeholder에 계속 표시한다.

UI 표시

상태PaneContainerControl 렌더링사용자 행동
Pending host 준비 전에는 빈 leaf 영역 또는 얇은 준비 상태 행동 없음
Ready 기존 TerminalHostControl 터미널 사용
Failed host 대신 실패 placeholder. stage, code, Retry button, close/split context 유지 Retry 또는 pane close
Retrying Retry button disabled, 짧은 진행 상태 중복 retry 방지

검증 계획

  • PaneLayoutService.AttachHostSurface unit test: SurfaceCreate=0이면 Failed 상태 기록, session 유지, resize skip.
  • latest resize cache test: 실패 중 resize가 오면 마지막 size를 저장하고 retry에 사용.
  • ViewModel projection test: failed surface snapshot이 leaf node에 실림.
  • STA/WPF test: failed pane은 HwndHost 대신 placeholder와 Retry button을 표시.
  • native test: null HWND, missing session, forced swapchain/RTV failure stage가 구조화되어 반환.
  • E2E hook: surface create를 첫 1회 실패시키고, Retry 후 terminal host가 표시되는지 확인.

11. 작업 전 확인할 위험

교착 상태 위험

SessionManager에 shared mutex를 추가할 때 callback과 TSF 호출을 lock 안에 두면 재진입으로 멈출 수 있다. 이 항목은 코드 변경 전 작은 설계 diff로 먼저 확인해야 한다.

HwndHost airspace

실패 placeholder를 child HWND 위에 overlay하면 WPF airspace 문제로 보이지 않을 수 있다. failed 상태에서는 host를 대체하거나 숨기는 방식으로 구현한다.

ClearState 부작용

resize 때 ClearState()를 쓰면 draw path가 모든 pipeline state를 다시 세팅해야 한다. 최소 해제인 OMSetRenderTargets(0,nullptr,nullptr)를 우선 검토한다.

device rebuild 범위

full device rebuild는 renderer, atlas, SurfaceManager까지 영향이 크다. 이번 cycle에서 감지/상태화까지 먼저 완료하고, 자동 rebuild는 검증 가능할 때 포함한다.

12. 요약 한 줄

이번 hardening의 목표는 pane tree를 더 예쁘게 조립하는 것이 아니라, 각 pane의 native surface가 focus, resize, device failure, session lifetime, creation failure 상황에서도 항상 일관된 상태로 보이거나 명확히 실패하도록 만드는 것이다.
