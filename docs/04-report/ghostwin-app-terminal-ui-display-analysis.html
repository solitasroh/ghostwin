GhostWin.App 터미널 UI 표시 구조 분석

이 보고서는 GhostWin.App에서 터미널이 화면에 나타나는 경로를 WPF visual tree, Services/Interop 경계, native DX11 render loop까지 연결해 정리한 결과다. 결론은 명확하다: WPF는 창과 입력 라우팅을 맡고, 실제 터미널 픽셀은 pane별 Win32 child HWND와 DX11 surface가 그린다.

목차

요약 현재 표시 구조 생성 수명주기 책임 분담 Native 렌더 경로 주요 리스크 다음 작업 후보 근거 파일

요약

GhostWin.App의 터미널 표시는 “WPF 안에 터미널을 직접 그리는 방식”이 아니다. WPF는 HwndHost로 child HWND를 만들고, native engine이 그 HWND에 pane별 DXGI swapchain을 붙인다. 렌더 스레드는 각 surface를 순회하며 VT frame, selection, IME overlay, padding, dim overlay를 DX11 quad로 그린다.

핵심 경계 TerminalHostControl : HwndHost가 WPF와 Win32/DX11의 실제 경계다.
렌더 소유권 텍스트 셀, 선택 하이라이트, IME preview는 WPF overlay가 아니라 DX11 overlay다.
다음 위험 focus dim invalidation, surface resize race, session lookup race가 다음 기획의 핵심이다.
분석상 중요한 정정: Obsidian의 일부 milestone 문서는 M-16-C를 아직 후보처럼 설명하지만, repo archive와 현재 코드는 M-16-C/D/F 일부 구현이 이미 들어온 상태다. 다음 기획 전에 문서 sync가 필요하다.

현재 표시 구조

사용자가 보는 터미널 영역은 MainWindow.xaml의 terminal border 안에 들어 있는 PaneContainerControl에서 시작한다. 이 컨트롤은 active workspace의 pane tree를 재귀적으로 WPF Grid로 만들고, leaf마다 TerminalHostControl을 배치한다.

WPF Shell
MainWindow는 Sidebar, NotificationPanel, SettingsPage, PaneContainer를 조립한다. 터미널 영역은 settings가 열리면 숨겨지고, 일반 상태에서는 PaneContainerControl이 표시된다.
Pane Tree
PaneContainerControl.BuildElement()는 split node를 Grid + GridSplitter로, leaf node를 Border + TerminalHostControl + ScrollBar로 만든다.
Win32 경계
TerminalHostControl.BuildWindowCore()가 GhostWinTermChild child HWND를 만들고, 이 HWND가 DXGI swapchain의 target이 된다.
Native Surface
PaneLayoutService.OnHostReady()가 IEngineService.SurfaceCreate()를 호출해 native RenderSurface를 생성한다.

Visual Tree 요약

MainWindow : FluentWindow
└─ content Grid
   ├─ Sidebar
   ├─ NotificationPanelControl
   ├─ SettingsPageControl
   └─ Terminal Border
      └─ PaneContainerControl : ContentControl
         └─ split node: Grid + GridSplitter + recursive children
         └─ leaf node: Grid
            ├─ Border
            │  └─ TerminalHostControl : HwndHost
            │     └─ Win32 child HWND "GhostWinTermChild"
            ├─ zero-size UIA probe Button
            └─ vertical ScrollBar

생성 수명주기

초기 pane blank 문제를 막기 위해 초기화 순서가 강하게 고정되어 있다. PaneContainer.Initialize()는 runtime service를 동기 주입하고, renderer 초기화 뒤 workspace를 만들거나 복원한다. workspace/pane 메시지는 TerminalPaneLayoutViewModel이 snapshot으로 투영하고, PaneContainerControl.Layout 바인딩이 visual tree를 만든다.

1. App Loaded MainWindow.OnLoaded에서 engine, session, workspace service를 가져온다.
2. Renderer Init RenderInit(IntPtr.Zero)로 hwnd-less renderer를 준비한다.
3. Workspace workspace 생성/복원 메시지가 TerminalPaneLayoutViewModel로 전달되고 Layout snapshot이 갱신된다.
4. Host HWND TerminalHostControl이 child HWND를 만든 뒤 HostReady를 발행한다.
5. Surface ITerminalSurfaceCoordinator가 HostReady를 pane layout의 surface attach로 라우팅한다.
단계 주요 파일 핵심 의미
Renderer 준비 MainWindow.xaml.cs:771, ghostwin_engine.cpp:525 전역 swapchain이 아니라 per-pane surface를 위한 renderer/device/atlas만 준비한다.
Host 생성 PaneContainerControl.cs:295, TerminalHostControl.cs:88 WPF visual leaf가 생기고, 실제 Win32 child HWND가 생성된다.
Surface 연결 PaneLayoutService.cs:268, surface_manager.cpp:65 native surface가 HWND에 swapchain/RTV를 붙인다.
Resize TerminalHostControl.cs:177, PaneLayoutService.cs:290 WPF size 변화가 child HWND resize와 native SurfaceResize로 이어진다.
Destroy PaneLayoutService.cs:164, surface_manager.cpp:88 surface는 deferred destroy로 render snapshot 사용 뒤 해제된다.

책임 분담

현재 구조는 “어디에 그릴 것인가”보다 “어느 계층이 어떤 입력과 시각 상태를 소유하는가”가 더 중요하다. Airspace 때문에 WPF overlay로 얹을 수 없는 것들은 native render path에 들어가 있다.

기능 소유 계층 현재 방식
창 / chrome / sidebar / settings WPF App MainWindow, ViewModel, ResourceDictionary가 처리한다.
Pane tree Services + WPF Control PaneLayoutService가 상태를, PaneContainerControl이 visual tree를 소유한다.
터미널 화면 픽셀 Native DX11 pane별 RenderSurface와 render thread가 그린다.
키 입력 MainWindow 단축키/Tab/chrome focus를 분류한 뒤 일반 입력은 WriteSession으로 보낸다.
마우스 입력 TerminalHostControl + native encoder child HWND WndProc에서 ghostty mouse encoder로 보내고, 미보고 시 selection 처리한다.
Selection WPF state + native overlay 범위 계산은 host가 하고, 시각 하이라이트는 gw_session_set_selection 이후 DX11이 그린다.
IME preview WPF single owner + native overlay TextCompositionPreviewController가 SetComposition으로 preview를 밀고, DX11이 cursor 위치에 그린다.
Mouse cursor shape Native callback + WPF host ghostty callback이 C#으로 올라오고, SetCursor로 Win32 cursor를 적용한다.
두꺼워진 컴포넌트: TerminalHostControl은 HwndHost lifecycle, WndProc, mouse forwarding, selection, cursor, context menu, external launcher까지 가진다. PaneContainerControl도 host cache, visual rebuild, scrollbar polling, focus visuals, context menu, zoom을 같이 가진다.

Native 렌더 경로

render loop는 16ms 단위로 active surface snapshot을 가져온다. 각 surface는 session의 VT state와 visual state를 읽고, 필요할 때만 quad를 만들어 Present한다. 

render_loop()
  └─ active_surfaces()
     └─ render_surface(surface)
        ├─ session_mgr->get(surface.session_id)
        ├─ state.start_paint(vt_mutex, vt)
        ├─ visual_state.snapshot()
        ├─ skip if !vt_dirty && !visual_dirty && !resize_applied
        ├─ QuadBuilder.build(frame)
        ├─ append selection overlay
        ├─ append IME composition overlay
        ├─ apply pad_left / pad_top to quads
        ├─ append dim overlay
        └─ upload_and_draw() + Present()

이미 구현된 표시 품질 요소

요소 구현 상태 근거
2-pass background/text 구현됨 CJK wide glyph 덮임을 줄이기 위해 배경 pass 뒤 텍스트 pass를 수행한다.
Selection overlay 구현됨 반투명 blue quad를 render thread에서 추가한다.
IME composition overlay 구현됨 composition text, underline, caret를 cursor 위치에 그린다.
Residual padding balance 구현됨 resize 때 남는 픽셀을 좌우/상하로 나누고 quad 좌표와 mouse 좌표에 반영한다.
Unfocused pane dim 구현됐지만 invalidation 위험 dim_factor 변경이 render dirty reason으로 연결되지 않는다.
Cursor shape/blink 단순 구현 terminal cursor는 hard-coded full-cell gray quad 중심이다.

주요 리스크

핵심 VT frame read path는 M-14의 FrameReadGuard와 SessionVisualState로 많이 정리되어 있다. 하지만 terminal display 품질과 직접 연결되는 surface/focus/resize 경계는 아직 다음 작업 가치가 크다.

Focus dim invalidation dim_factor만 바뀌면 visual_dirty가 변하지 않아 repaint가 skip될 수 있다.
Surface resize race pending_w/h는 plain field이고 render thread가 lock 없이 읽는다.
ResizeBuffers 복구 surface path의 ResizeBuffers는 HRESULT 처리와 context unbind가 약하다.
Session lookup race render thread가 session_mgr->get()을 호출하고 create/close와 겹칠 수 있다.
SurfaceCreate 실패 현재는 0 반환 시 로그만 남고 pane은 blank가 된다. retry/recover API가 없다.
렌더 호환성 bold/italic/strike/faint/blink, atlas grow, device lost recovery가 후속 품질 과제다.

리스크 우선순위

순위 작업 왜 먼저인가
1 Focus dim repaint epoch 연결 사용자가 바로 보는 pane focus 표시가 다음 output 전까지 갱신되지 않을 수 있다.
2 Surface resize payload 원자화 빠른 resize/split 중 plain field race 가능성이 있다.
3 Session registry snapshot/lock close/split/reopen 중 render thread가 stale session을 볼 수 있다.
4 ResizeBuffers failure handling DXGI 실패 시 blank/stale surface로 남는 문제를 줄인다.
